# Реальный локальный ИИ

`libchits_ai.so` выполняет CPU-инференс GGUF через llama.cpp. Здесь нет удалённого API, подмены ответов шаблонами или загрузки модели на сервер. Готовая библиотека предназначена для **64-битного ARM Android 8.0+**; Для текстовой модели 0,5B достаточно небольшой части 8 ГБ ОЗУ. Для фото используется более тяжёлая модель 3B с проектором: доступной памяти может хватить, но это зависит от свободной памяти, процессора и ограничений Android. Производительность на телефоне ещё не измерена.

Веса модели не входят в APK. Их нужно один раз скачать в приложении или импортировать локальный GGUF. После успешной загрузки файл остаётся во внутреннем хранилище, и ответы генерируются без интернета. Удаление приложения удаляет этот файл.

Совместимая компактная текстовая модель — `Qwen/Qwen2.5-0.5B-Instruct-GGUF`, файл `qwen2.5-0.5b-instruct-q4_k_m.gguf`, около 400 МБ. Для загрузки приложение сначала получает неизменяемую ревизию официального репозитория Hugging Face и метаданные LFS SHA256/размер, затем скачивает файл именно этой ревизии и проверяет целостность. Доступность модели и качество ответов на настоящем телефоне ещё нужно проверить; наличие успешной сборки не заменяет этот тест. Модель значительно меньше современных облачных помощников: её ответы могут ошибаться.

## Понимание фото

Реализован **настоящий мультимодальный инференс** через upstream `libmtmd`: JPEG/PNG декодируются локально, изображение проходит vision encoder/проектор, его embeddings попадают в языковую модель, и ответ генерируется на CPU телефона. Фотографии не отправляются на сервер. Размер фото внутри native-движка ограничен 560 пикселями по длинной стороне с сохранением пропорций, чтобы снизить потребление памяти и время обработки. Это ограничивает чтение мелкого текста и деталей: модель может ошибаться.

Профиль: **`ggml-org/Qwen2.5-VL-3B-Instruct-GGUF`**, поддерживаемый закреплённой версией llama.cpp (он указан в `docs/multimodal.md` upstream и в тестах mtmd). Нужны **два** совместимых файла одной неизменяемой ревизии: языковая модель `Q4_K_M` и `mmproj` (Q8_0 при наличии, иначе F16). Имена, размеры и SHA256 получают из фактических HF-метаданных, а не придумывают. Объём обоих файлов — ориентировочно 3–4 ГБ; показывать пользователю следует фактический размер из метаданных. Загрузка весов и реальные ответы на фотографии в этой облачной среде не проверены.

Vision-контекст содержит 4096 токенов. Для контроля ёмкости используются занятые KV-токены изображения, а продолжение генерации использует временные позиции M-RoPE, возвращённые mtmd. Изображение и проектор освобождаются перед языковой моделью. Старый текстовый путь 0,5B сохранён.

## Сборка

Из каталога проекта:

```sh
bash ai-native/build.sh
```

Сценарий сохраняет инструменты и сборочный кэш в `/workspace/.chits-tools` (можно задать `CHITS_TOOLS_DIR`), собирает с шестью процессами (`CHITS_BUILD_JOBS`) и копирует результат в `app/src/main/jniLibs/arm64-v8a/libchits_ai.so`. Исходный код приложения и веса не передаются внешним сервисам.

Зафиксированные источники:

- llama.cpp, официальный GitHub `ggml-org/llama.cpp`, tag `b6500`, commit `a7a98e0fffed794396b3fbad4dcdbbc184963645` (MIT; текст в `LICENSE.llama.cpp`).
- Android NDK r27d `27.3.13750724`, официальный `https://dl.google.com/android/repository/android-ndk-r27d-linux.zip`. SHA-1 `22105e410cf29afcf163760cc95522b9fb981121` взят из официального `repository2-1.xml`; сценарий проверяет его до распаковки.
- Вспомогательные кодеки из того же закреплённого дерева: stb_image (MIT/public domain, `LICENSE.stb_image`) и miniaudio (MIT No Attribution/public domain, `LICENSE.miniaudio`); оба включаются upstream mtmd-helper.
- CMake `3.31.10` и Ninja `1.13.0`, PyPI по HTTPS с обычной проверкой TLS.

Используется baseline `armv8-a` без требования новых CPU-инструкций; C++ runtime статический; ELF LOAD-сегменты выровнены по 16 КиБ. Системные зависимости: `libc.so`, `libm.so`, `libdl.so`.

## Java/JNI

`market.chits.OfflineAi`:

- `isSupported()` — удалось ли загрузить native-библиотеку.
- `load(absoluteGgufPath)` — загрузить модель и контекст 2048 токенов.
- `load(absoluteGgufPath, absoluteProjectorPath)` — vision-модель с контекстом 4096 токенов.
- `generate(userMessage, imagePath, maxTokens)` — ответ по локальному изображению.
- `hasVision()` — загружен совместимый vision-проектор.
- `generateStreaming(userMessage, imagePath, maxTokens, Listener)` — настоящий поток генерируемых токенов.
- `cancel()` — потокобезопасная отмена без ожидания блокировки генерации.
- `generate(userMessage, maxTokens)` — русский системный промпт, шаблон диалога модели, не более 256 новых токенов.
- `isLoaded()` и `release()`.

Повторный `load` использует уже загруженную модель и проектор, если канонические пути, размеры, время изменения файлов и режим совпадают. Он не перечитывает несколько гигабайт на каждый вопрос. Смена режима, изменение файлов, ошибка загрузки и `release()` сбрасывают кэш. Полный хеш больших весов на каждый вопрос не вычисляется: проверка SHA256 относится к загрузке/импорту.

`Listener.onPartial(String cumulative)` вызывается на рабочем потоке сразу при появлении первого полного символа, далее через 100 мс или после накопления 16 новых байт. Неполные UTF-8 символы удерживаются до следующих токенов; кириллица и emoji не разрезаются. Это реальные промежуточные токены, а не анимация готового ответа. UI необходимо обновлять через основной поток. Не вызывайте загрузку/генерацию/освобождение модели из этого callback.

`cancel()` не синхронизируется с Java-монитором или native-mutex генерации: атомарный флаг проверяется в CPU abort callback `llama_decode`. Генерация возвращает уже полученную часть ответа. Vision-encoder upstream не имеет публичного mid-encode abort callback, поэтому отмена во время кодирования фотографии применяется на следующей безопасной границе. Каждый запрос фиксирует эпоху отмены до входа в native-код; отмена между фиксацией запроса и генерацией не теряется. Вызывающая сторона дополнительно проверяет свой флаг после загрузки модели, чтобы не начинать генерацию отменённого до входа в Java-метод запроса. Потоки CPU ограничены доступными ядрами, максимум четыре; это не обещание конкретной скорости.

Все операции загрузки, генерации и освобождения запускаются вне UI-потока. Java и JNI синхронизируют доступ к модели; GPU и OpenMP не используются. JNI возвращает UTF-8 как байты, поэтому кириллица и emoji не проходят через несовместимый `NewStringUTF`. Длинный промпт отклоняется с ошибкой, без молчаливой потери контекста. История автоматически не хранится: передаваемый текст — отдельный запрос.

## Полезная проверка без весов

На Linux-хосте можно собрать реальный upstream-декодер и проверить чтение PNG, RGB-значения, bilinear resizing, сохранение пропорций, ограничение памяти 560px и отказ на повреждённых данных:

```sh
CHITS_TOOLS_DIR=/workspace/.chits-tools
"$CHITS_TOOLS_DIR/python-tools/cmake/data/bin/cmake" -S ai-native -B "$CHITS_TOOLS_DIR/ai-image-host-test" -G Ninja \
  -DCMAKE_MAKE_PROGRAM="$CHITS_TOOLS_DIR/python-tools/bin/ninja" \
  -DLLAMA_SOURCE_DIR="$CHITS_TOOLS_DIR/llama.cpp" -DCHITS_BUILD_IMAGE_TESTS=ON -DCMAKE_BUILD_TYPE=Release
"$CHITS_TOOLS_DIR/python-tools/cmake/data/bin/cmake" --build "$CHITS_TOOLS_DIR/ai-image-host-test" --target chits_image_test chits_generation_test -j 6
"$CHITS_TOOLS_DIR/python-tools/cmake/data/bin/ctest" --test-dir "$CHITS_TOOLS_DIR/ai-image-host-test" --output-on-failure
```

Эта проверка не подтверждает семантическое понимание фото. Для него нужны настоящие веса модели и запуск на Android: выбрать фото, дождаться генерации, повторить при отключённом интернете.

Дополнительная проверка жизненного цикла Java:

```sh
bash ai-native/tests/run_cache_test.sh
```

Она использует явно тестовую JNI-библиотеку-счётчик и проверяет предотвращение повторных загрузок, инвалидацию при изменениях/ошибках и неблокирующий вход `cancel()`. Она не проверяет нейросетевые ответы. CTest дополнительно проверяет реальные CPU-вычисления ggml с прерыванием, а также UTF-8 границы и частоту передачи текста. Скорость первого/повторного ответа с настоящими весами на телефоне пока не измерена.
