# Chits Market на Firebase

Этот вариант заменяет собственный Python API управляемыми сервисами Firebase: Hosting открывает веб-маркет, Authentication проверяет администратора, Firestore хранит каталог, Cloud Storage хранит APK. Старый Python-сервер остаётся отдельным резервным вариантом. Публикация Firebase здесь пока не выполнялась: нужны настройки вашего проекта и доступ владельца.

## Что нужно подготовить

1. Создайте или выберите свой проект Firebase. Добавьте веб-приложение и скопируйте его **публичный** Firebase Web config.
2. В Authentication включите провайдер **Email/Password**. Выберите реальный email администратора; в интерфейсе магазина никнейм останется `Leon_Salimov`.
3. Создайте базу Firestore в подходящем регионе и бакет Cloud Storage. Не используйте публичные «тестовые» правила доступа.
4. Проверьте тариф и лимиты. **Cloud Storage for Firebase требует подключённого биллинга (Blaze)**; создание/использование бакета может приводить к расходам. Этот код и сценарии **не подключают биллинг, не создают бакет и не активируют платные сервисы**. Если вы не хотите подключать биллинг, загрузки APK через Firebase Storage не заработают; используйте прежний сервер или локальные APK. [Официальная информация об изменениях Storage](https://firebase.google.com/docs/storage/faqs-storage-changes-alert), [тарифы](https://firebase.google.com/pricing).

Не присылайте JSON сервисного аккаунта, приватные ключи, OAuth-токены или пароль в исходники/чат. Для настройки интерфейса нужны только публичные поля из `config.example.json` и email администратора. Firebase `apiKey` веб-приложения идентифицирует проект; доступ администратора он не даёт.

## Подключение приложения

В Android-маркете откройте «Настройки» → Firebase и вставьте публичный JSON:

```json
{
  "enabled": true,
  "apiKey": "значение apiKey вашего веб-приложения",
  "authDomain": "ваш-проект.firebaseapp.com",
  "projectId": "ваш-проект",
  "storageBucket": "точное имя бакета из Firebase Console",
  "appId": "значение appId вашего веб-приложения",
  "adminEmail": "ваш-настоящий-email@example.org"
}
```

Нужен точный `storageBucket` из проекта: у новых и старых бакетов окончания различаются. Пароля и сервисного ключа в этом JSON быть не должно. Сохранение публичной конфигурации на телефоне не требует пересборки APK и не развёртывает правила на сервере.

Для веб-версии заполните публичную конфигурацию в `app/src/main/assets/web/firebase-config.js` и опубликуйте Hosting после проверки. По умолчанию Firebase выключен, а конфигурация пуста. Если на телефоне уже сохранены настройки Firebase, обновление APK не должно молча заменять их.

## Инструменты и правила доступа

Нужны Node.js 22+, npm и Java 21 для локальных эмуляторов. Из каталога `firebase`:

```sh
npm ci
npm run test:provision
npm test
```

Все зависимости закреплены lockfile. Эмуляторы используют проект `demo-chits-market`; тесты не обращаются к настоящей базе и не требуют биллинга. При первом запуске Firebase CLI скачивает официальные файлы эмуляторов, поэтому нужен сетевой доступ к их источникам.

Правила устроены так:

- Каталог `/apps/{id}` можно читать всем. APK можно скачать по известному пути `apks/{id}.apk`; публичного списка файлов бакета нет.
- Создавать/менять/удалять записи каталога и APK может только Firebase Auth-пользователь с **custom claim `chitsAdmin: true`**.
- Обычная регистрация, знание email/никнейма и публичного Web config прав администратора не дают.
- Роль назначается только доверенным Firebase Admin SDK. Клиентам запрещено писать в коллекции ролей и любые другие коллекции.
- Проверяются поля каталога, допустимые пути и MIME, размер APK до 200 МБ и формат SHA-256. Правила не вычисляют хеш файла и не проверяют APK на вирусы: загрузчик рассчитывает SHA-256, а Android-клиент сверяет его после скачивания и проверяет APK перед установкой.

Нельзя безопасно заменить эти правила на `allow write: if true` или просто `request.auth != null`.

## Создание администратора

Выполните на доверенной машине, авторизованной для **вашего** проекта. Firebase CLI-вход и credentials Admin SDK — разные вещи. Сценарий использует **Application Default Credentials**: например, существующую настроенную облачную identity, локальный `gcloud auth application-default login` либо путь `GOOGLE_APPLICATION_CREDENTIALS` к защищённому сервисному ключу. Не копируйте содержимое ключа в проект. Используйте минимальные права для управления Firebase Authentication.

```sh
node provision-admin.mjs --project YOUR_PROJECT_ID --email YOUR_ADMIN_EMAIL
```

Если аккаунта нет, пароль запрашивается скрытым вводом; сохраните желаемый пароль и войдите с ним в маркете. Для автоматизации можно использовать `--password-stdin` либо переменную `CHITS_FIREBASE_ADMIN_PASSWORD`, но не аргумент командной строки. Сценарий не печатает пароль и не записывает его в исходники. Для существующего пользователя пароль сохраняется; смена выполняется только с явным `--reset-password`.

Сценарий назначает `chitsAdmin: true`, сохраняет другие custom claims и выводит UID/email без секретов. После назначения роли **выйдите и войдите заново**, чтобы обновился Firebase ID token. Email должен совпадать с `adminEmail` публичной конфигурации. Роль задаётся UID-токеном, а не текстовым никнеймом.

Для снятия роли:

```sh
node provision-admin.mjs --project YOUR_PROJECT_ID --email YOUR_ADMIN_EMAIL --revoke-admin
```

Refresh-токены отзываются; уже выданный ID token может действовать до своего стандартного срока, обычно до часа. Не считайте снятие роли мгновенной блокировкой всех ранее выданных ID-токенов.

## Развёртывание

После проверки проекта, настроек доступа и тарифа, из `firebase`:

```sh
npx firebase login
npx firebase deploy --project YOUR_PROJECT_ID --only firestore:rules,firestore:indexes,storage,hosting
```

Команда публикует реальные изменения именно в указанном проекте. До выполнения проверьте, что `YOUR_PROJECT_ID` заменён своим ID. Hosting берёт файлы непосредственно из `../app/src/main/assets/web`; домен Hosting появляется в результате успешной публикации. Не выдумывайте URL до подтверждения развёртывания. Установите бюджет/уведомления в Google Cloud и следите за расходами; лимиты уведомлений не равны автоматическому прекращению расходов.

Firebase Storage и Firestore не поддерживают одну общую атомарную транзакцию. Загрузка клиента сначала сохраняет APK, затем документ каталога; при неудаче второй операции файл следует удалить. Удаление из маркета также должно обрабатывать обе операции. Уже скачанные на телефон APK остаются доступными офлайн.

## Контракт данных

Firestore: коллекция `apps`, документ с ID `[A-Za-z0-9_-]{1,100}`. Обязательные поля:

| Поле | Значение |
|---|---|
| `id` | Совпадает с ID документа |
| `title`, `description`, `category` | Строки: название 1–120, описание до 5000, категория 1–60 символов |
| `versionName`, `packageName` | Строки до 80/200 символов; если браузер не разобрал бинарный манифест, допустимы `APK` и пустой пакет |
| `size` | Целое число байт, 1–209715200 |
| `sha256` | 64 строчных шестнадцатеричных символа |
| `storagePath` | Строго `apks/{id}.apk` |

Дополнительно разрешены `fileName` (строка до 180 символов) и `createdAt`/`updatedAt` (Firestore timestamps). Другие поля запрещены. Адрес скачивания вычисляется клиентом: `https://firebasestorage.googleapis.com/v0/b/{bucket}/o/{urlEncodedStoragePath}?alt=media`.

Storage при загрузке требует MIME `application/vnd.android.package-archive` или `application/octet-stream` и **custom metadata `sha256`** в том же формате. Это не серверный пересчёт хеша, а проверяемый контракт доверенного администратора. Клиент должен использовать поддерживаемый Firebase multipart upload с metadata и двоичными данными.

## Проверка после публикации

Откройте выданный Hosting URL, проверьте каталог и вход администратора. Загрузите тестовый APK, скачайте его на телефон, затем отключите Интернет и установите из «Загрузок» через системное подтверждение Android. Проверьте, что без входа и с обычным аккаунтом публикация/удаление запрещены. Удалите тестовую запись. Только успешная публикация и эти проверки подтверждают готовность настоящего проекта; локальные тесты сами по себе этого не доказывают.
